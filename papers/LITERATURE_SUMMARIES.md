## Teaching Operating Systems Using Virtual Appliances and Distributed Version Control

**Citation:** Oren Laadan, Jason Nieh, and Nicolas Viennot (2010). Teaching Operating Systems Using Virtual Appliances and Distributed Version Control. Proceedings of SIGCSE '10, March 10–13, 2010, Milwaukee, Wisconsin, USA. ACM 978-1-60558-885-8/10/03, pages 480–484 (no DOI printed in the PDF).
**Filename:** `Teaching OS.pdf`

**What it is:** This is an experience paper from Columbia University describing a new approach to managing and grading operating systems homework built on three components: pre-configured virtual appliances that students run on their own laptops, a Git-based distributed version control workflow for storage and submission, and live demonstrations for grading kernel projects. The core claim is that this combination eliminates the need for a dedicated computer laboratory while supporting the most demanding coursework, including Linux kernel development, for both on-campus and remote distance-learning students.

**Setting & method:** The setting is the operating systems course at Columbia University's Department of Computer Science, which the authors state they have taught "for almost ten years using various forms of virtualization," with students working in groups of two or three on Linux kernel development assignments. The study design is a qualitative, comparative experience report rather than a controlled experiment: the authors compare three infrastructure generations they used over the years — a shared computer laboratory of Linux desktops running VMware Workstation, a centralized server cluster with SAN storage running VMware ESX, and finally the virtual-appliance-plus-Git solution used for the most recent year — and report observed operational problems and student and instructor reactions. No enrollment counts, surveys, statistical measures, or learning-outcome metrics are reported; what is "measured" is qualitative ease of use, flexibility, and pedagogical effectiveness as judged by instructor experience.

**Key findings:**
- The bzip2-compressed virtual appliance, built on a stripped-down Gentoo Linux base (no mail, cron, syslog, HAL, D-Bus, ALSA, Bluetooth, WiFi, or ACPI services), was only 240 MB, "which downloads in only a few minutes for most network connections."
- Live grading demonstrations were run in assigned 20-minute time slots during office hours, with an automated build process generating a bootable kernel image from each submission so staff never had to manually install, reboot, and test each one.
- Git repositories were secured with standard UNIX permissions (`chmod 740`, accessible only to the student and instructional staff), server-side push logging (date, username, object hashes) enforced tamper-proof submission deadlines, and pushes after the deadline were rejected; commit timestamps were deliberately not trusted because students can manipulate them.
- Git clone hardlinking meant each student repository stored "only diffs from the template" kernel tree, keeping storage modest even though every repository contained a full Linux kernel tree.
- The earlier centralized ESX/SAN infrastructure "became noticeably slow right before homework assignments were due when it was being used by everyone intensively at the same time," and snapshot abuse "filled up the entire multi-TB SAN"; the shared desktop lab required support staff intervention for every VMware install and hardware failure.
- On the overall result: "Our experiences deploying and using this solution to teach operating systems at Columbia University show that it is easier to use, more flexible, and more pedagogically effective than other approaches."
- The conclusion asserts the approach "is cost-effective, easy to deploy and use, and improves the educational experience of students in learning about operating systems," and the work was supported in part by VMware and NSF grants CNS-0426623, CNS-0717544, and CNS-0914845.

**Technical approach:** The system is a pre-built Linux virtual appliance — a ready-to-run VM bundle requiring no installation or configuration — created by instructional staff with the OS, development tools, and version control pre-installed, then compressed and distributed from the class web site. Students run it under VMware Workstation 6.5 (Windows/Linux) or VMware Fusion 2.0 (Mac), obtained free through academic licensing. The base system is a minimal, source-optimized Gentoo Linux chosen for small disk footprint and fast boot (important for the reboot-heavy kernel test cycle); the disk was shrunk by zero-wiping free space (`dd if=/dev/zero of=tmp; sync; rm tmp`) and running vmware-vdiskmanager. Version control is Git, chosen over CVS for its distributed, offline-capable design; a Git server (which "can be used with any backed up machine," even a VM on an instructor's desktop) hosts per-student repositories cloned from a template kernel repository, with students restricted to `/usr/bin/git-shell` accounts accessed over SSH keys. The same Git system handles reliable storage, group collaboration, progress monitoring via check-in logs, deadline enforcement, and staff feedback via comments committed directly into student code (staff use `//` comments to distinguish from students' `/* */`). Grading is completed through live demonstrations in which students boot an automatically built kernel image from their submitted code inside a clean appliance.

**Limitations the authors acknowledge:** The authors acknowledge that using appliances on student-owned machines means instructional staff no longer have easy access to students' virtual machines, and that students' personal computers are often not backed up, which is precisely the gap the Git server was added to fill. They also note that commit timestamps cannot be trusted for deadline enforcement, requiring server-side logging instead, and that having students check entire appliances into version control would incur too much storage overhead, motivating the live-demonstration workaround. More broadly, the evaluation is presented only as accumulated instructor experience across infrastructure generations, with no quantitative learning outcomes; the paper itself does not frame this as a limitation, but it reports no measured comparison data.

**Relevance to the UNLV Docker IDE paper:** This is arguably the earliest prior-work lineage for the UNLV paper's core motivation — distributing a pre-configured, identical course environment to students' own heterogeneous laptops so that everyone runs exactly the same compilers and OS versions — with Docker images and code-server playing the role that VMware virtual appliances played in 2010. It supplies a strong contrast case for the technology-generation shift: a 240 MB full-VM appliance requiring a commercial hypervisor versus OCI images with multi-arch manifests, and notably the appliance approach sidestepped the ISA problem entirely (a VM presents whatever the host CPU offers), whereas the UNLV assembly image must deliberately pin amd64 and document the gdb/ptrace-under-QEMU limitation on Apple Silicon — a hardware-heterogeneity issue that did not exist in the all-x86 era of this paper. Methodologically, it is a template and a caution: like the UNLV paper, it is an experience report comparing infrastructure designs qualitatively rather than with controlled outcome measures, so citing it supports the legitimacy of that genre while highlighting the value of any concrete numbers (image sizes, pull times) the UNLV paper can offer. Finally, its emphasis on local execution enabling offline work and eliminating lab and network-security concerns maps directly onto the UNLV localhost-only, local-single-user threat-model framing.

## From Cluster to Cloud to Appliance

**Citation:** David J. Malan (2013). From Cluster to Cloud to Appliance. ITiCSE '13 (18th Annual Conference on Innovation and Technology in Computer Science Education), July 1–3, 2013, Canterbury, England, UK. ACM 978-1-4503-2078-8/13/07 (no DOI printed in the PDF).
**Filename:** `Cluster to Cloud.pdf`

**What it is:** This experience paper proposes a client-side virtual machine, the CS50 Appliance, as an alternative to on-campus Linux clusters and off-campus clouds as the development environment for students in Harvard's introductory CS50 course. It reports the results of a two-year deployment experiment (Fall 2011 and Fall 2012) covering both on-campus students and a massive online cohort via edX. The appliance itself is released as open source at http://cs.harvard.edu/malan for other courses to adapt or adopt.

**Setting & method:** The setting is Harvard University's CS50, a one-semester introductory course taught mostly in C in a command-line environment, with PHP and SQL introduced toward term's end; in Fall 2012 enrollment was 715, 73% of whom had no prior CS experience. The appliance was deployed to 607 on-campus students in Fall 2011 and to 715 on campus plus over 140,000 students online in Fall 2012, after the course had previously used a load-balanced SSH cluster of Linux servers and, from Fall 2009, server-side VMs on Amazon EC2. The study design is a descriptive two-year deployment experiment; measurements came from end-of-term student surveys assessing the appliance's perceived performance plus staff observations of technical difficulties, RAM profiles of students' laptops, and hardware age.

**Key findings:**
- All Fall 2011 on-campus students used the appliance for 8 problem sets (both C- and web-based), and many used it for final projects; overall the author judges the two-year experiment a success, "superior to past years' clusters and clouds."
- On surveys in both years, most students rated the appliance's performance as "fast" or "fine," but "just under 20% found the appliance to be 'slow,'" though some of those students disclaimed that their own computer was slow.
- Insufficient RAM was often the culprit for slowness: nearly 20% of students had computers with only 2 GB of RAM, nearly 3% had even less, and just over 6% had computers at least 4 years old.
- Corruption of students' virtual disks under VirtualBox was "surprisingly frequent," ultimately traced to students closing laptop lids with the appliance still running; the course switched its recommendation to VMware Player and Fusion in Fall 2012, which tolerate that behavior better.
- The appliance eliminated the need for constant Internet access, distributed execution across students' own CPUs, and relieved server load before deadlines: "Without the appliance (or more costly clusters or clouds), we certainly could not have accommodated as many as 140,000 students."
- Fall 2012 added Dropbox-based file sync (free up to 2 GB) so "each student's appliance would be effectively disposable" — a failed appliance could be reconstituted and files resynced within minutes; the appliance also runs rsnapshot internally to back up files locally every few minutes.
- Downsides persisted: staff could no longer resolve technical difficulties server-side (though TeamViewer screen-sharing helped), mid-semester mistakes in the appliance's configuration required yum-delivered updates, and in Fall 2012 just under 20% of on-campus students still found the appliance slow.

**Technical approach:** The lineage runs from a load-balanced on-campus SSH cluster (gcc/gdb), to server-side VMs recreated on Amazon Elastic Compute Cloud in Fall 2009 (giving staff root access and elastic scaling but costing sysadmin time and adding X-application latency, e.g. for emacs), to the client-side CS50 Appliance in Fall 2011. The appliance is a preconfigured VM running 32-bit Fedora (32-bit chosen "for compatibility's sake"), distributed as a ZIP of two files — a machine-readable virtual-hardware description and one binary virtual-disk file — and run under a free hypervisor (VirtualBox initially; VMware Player/Fusion recommended in Fall 2012, with Fusion licenses free to students via a VMware Academic Program subscription paid by the course, and free 6-month licenses arranged for edX students). The disk image is built reproducibly from two artifacts, appliance50.ks (an Anaconda kickstart file) and appliance50.rpm (a package completing configuration and delivering semester-long updates via yum). Booted, it provides a command line with gcc, gdb, and make, an Xfce desktop with gedit (embedded terminal plus syntax highlighting) as the chosen editor, server software (Apache, MySQL) for late-term web work, additional languages (g++, java, perl, python, ruby), sudo access, TeamViewer for staff remote assistance, and course tools check50, style50, and submit50; downstream courses can reconfigure it with a single command (e.g., `yum install cs51`).

**Limitations the authors acknowledge:** Some students' laptops, particularly netbooks, struggled under the weight of a VM, since an appliance "like any VM, still consumes resources, particularly RAM," and just under 20% of students in both years found it slow. The author made several mistakes in the appliance's configuration at term's start, and bugs in Fedora's rapid release cycle and in VirtualBox (including frequent virtual-disk corruption) caused unforeseen technical difficulties, most but not all of which were redressed with mid-semester updates and documentation. Staff also lost the ability to fix problems server-side, and off-cycle Fedora updates triggered unforeseen headaches even in Fall 2012. As future work the author notes the appliance remains a perpetual work in progress, proposes Puppet for configuration management, a 64-bit variant, a cloud AMI fallback for underpowered machines, and longer-term a web-based code editor and debugger to replace the appliance for some problem sets.

**Relevance to the UNLV Docker IDE paper:** This is arguably the closest prior work in spirit: like the UNLV Docker IDEs, the CS50 Appliance moves a standardized course environment onto student-owned hardware precisely to guarantee a uniform toolchain (gcc, gdb, make) for novices, and the UNLV containers are the natural next step in the same lineage — cluster to cloud to appliance to container — replacing a full Fedora VM with lightweight, localhost-only code-server containers. Malan's survey-based evaluation of perceived performance and his frank accounting of client-side failure modes (RAM pressure, hypervisor bugs, mid-semester image updates) provides a methodological template the UNLV paper can adopt for evaluating its own images. The paper is also a useful contrast case on architecture: Malan chose 32-bit x86 Fedora "for compatibility's sake" and later contemplated a 64-bit variant so student and server architectures would match, which directly parallels the UNLV decision to keep the assembly image amd64-only to preserve the course's real ISA and Linux ABI — including the honest documentation of the resulting gdb/ptrace limitation under QEMU on Apple Silicon, an architecture-fidelity trade-off Malan's era never had to confront. Finally, Malan's closing aspiration to replace the appliance altogether with a web-based code editor and debugger is essentially what the UNLV code-server approach realizes, letting the UNLV paper frame itself as fulfilling that trajectory while deliberately rejecting cloud hosting and AI assistance in favor of student-local, offline-capable containers.

## Virtualization for Cost-effective Teaching of Assembly Language Programming

**Citation:** Cadenas, J. O., Sherratt, R. S., Howlett, D., Guy, C. G., & Lundqvist, K. (2015). Virtualization for cost-effective teaching of assembly language programming. IEEE Transactions on Education, 58(4), pp. 282–288. ISSN 0018-9359. DOI: 10.1109/TE.2015.2405895.
**Filename:** `Virtualization of assembly.pdf`

**What it is:** This paper describes replacing physical embedded development boards with a QEMU-based full-system ARM emulator for teaching assembly language programming at the University of Reading. The virtual system runs a complete Linux operating system (Ubuntu 9.04) on an emulated ARM machine hosted on any standard x86 Windows or Linux PC, integrating all development tools (editor, assembler, compiler, linker, debugger) natively inside the guest. The authors present six years of assessment data showing a statistically significant improvement in lab marks after the virtual system was introduced.

**Setting & method:** The setting is the "Computer Architecture" module, a 100 contact-hour compulsory second-year module in the School of Systems Engineering, University of Reading, taken by Computer Science and Electronic Engineering students, with two hours of lecture plus two hours of laboratory per week across the academic year; the lab component contributes 30% of the final module mark. The old hardware-based lab was phased out in 2010 and the virtual system rolled in. Evaluation combined (1) a voluntary 15-question Likert-scale online survey administered since 2010 (completed by around 70% of students; N=237 for the five reported questions) and (2) final lab assessment marks over six academic years (2008–09 through 2013–14, three years old system and three years new system, N per year ranging from 36 to 76), analyzed with single-factor ANOVA and t-tests to separate the effect of the virtual system from a concurrent switch to online assessment.

**Key findings:**
- Survey (N=237, average percentages over three years): Q4 ("opportunity to experiment directly with the instruction set of the ARM processor") drew 13.5% Strongly Agree and 72.9% Agree; Q5 (clarity of instruction execution stages) drew 10.8% SA and 67.5% A; Q3 (assembly can speed up C code) drew 32.4% SA and 62.1% A, with 0.0% Strongly Disagree on all five reported questions.
- Only about 10% of students disagreed that they gained understanding of internal hardware organization (Q1: 10.8% SA, 51.3% A, 27.0% NAD, 10.8% D); on Q2 (confidence writing ARM assembly) responses were weaker: 2.7% SA, 45.9% A, 24.3% NAD, 24.3% D.
- Mean final lab marks (scaled 1–100): 2008–09: 56.3 (N=36, SD 16.8); 2009–10: 56.5 (N=45); 2010–11: 59.1 (N=61); 2011–12: 72 (N=76, SD 25.1); 2012–13: 73 (N=61, SD 19.6); 2013–14: 83 (N=50, SD 13.5, max 100).
- A t-test between 2010–11 and previous years showed no significant difference (p>30%) attributable to the introduction of online assessment, whereas "the same analysis between further years does indicate there is a very significant change (p<1%) across the marks after the new virtual system was introduced that cannot be attribute to the on-line assessment."
- Students feel real hardware is slightly preferable to emulation (5:4), but "even a small cost for a hardware kit put the preference back to the virtual system due to having no-cost while providing the flexibility of working anywhere/anytime rather than in scheduled labs (3:1)." In 2010, 30% of students felt Linux made the lab harder; by 2013 this dropped to under 15%. Over 90% of students consistently prefer online computer-based assessment over written reports.
- The educators estimate less-aware students need around 4–6 hours of familiarization with the virtual system and Linux; the whole system fits on a standard USB memory stick and requires about 1 GB of storage when uncompressed.
- "No software licenses or extra hardware are required to use the virtual system, thus students are free to carry their own ARM emulator with them on a USB memory stick."

**Technical approach:** The system is built on QEMU full-system emulation (`qemu-system-arm -M versatilepb -kernel Zimage -hda arm-lab.img -m 256`), emulating an ARM VersatilePB machine with 256 MB RAM (the maximum for that machine) on a native x86 Windows or Linux host. The guest runs a complete Linux OS: a Linux kernel cross-compiled for ARM (zImage) plus a 1 GB disk image (`arm-lab.img`) filled with an uncompressed Ubuntu 9.04 ARM root filesystem generated from Ubuntu's RootfsFromScratch scripts, with the lightweight LXDE X11 desktop installed for a graphical mode alongside a console-only mode. Crucially, because it is full-system emulation, the entire GNU toolchain runs natively inside the ARM guest: editors (vim, Leafpad, the Geany IDE), gcc, the assembler and linker, gprof for profiling, and GDB — "The GNU debugger (GDB) has been integrated for use within an assembly language program," with students setting breakpoints, stepping, examining registers (stack pointer, program counter), and walking the stack frame. No cross-compilers on the host are needed. Distribution is a compressed downloadable zip file hosted by the university (the whole system fits on a USB stick); a shared login ("arm") is preconfigured, students can map their university Network Drive between host and guest, students maintain the guest themselves via apt-get, and some students ported the emulator to Mac hosts and replicated the labs with clang instead of gcc. QEMU was chosen specifically because VMware and VirtualBox cannot emulate an ARM processor, and alternatives like SPIM, SimpleScalar, Bochs, and Simics were rejected (no full system, no ARM support, or license required).

**Limitations the authors acknowledge:** The emulator is slower than real hardware since many host instructions are needed per emulated instruction, and emulators require host storage and lack physical I/O devices; topics involving physical interfaces such as GPIO, timers, and interrupts are explicitly deferred to a different module that uses real PIC32 hardware. The lab was never delivered with a real ARM system, so the comparison to hardware-based teaching is indirect, and evidence that the labs replicate on real ARM systems (Raspberry Pi, phones, tablets) is student-reported and acknowledged as anecdotal. The mark improvement is entangled with a concurrent switch to online assessment (addressed statistically but noted as "a more complex scenario"), the school-wide feedback covers whole modules so the lab's contribution "can only be postulated," survey completion was voluntary at around 70%, and the cost saving "can be seen as modest, depending on the needs and resources of the end user." Cloud deployment is left as future work.

**Relevance to the UNLV Docker IDE paper:** This is the closest prior work for the UNLV assembly image and the natural anchor citation for the claim that virtualized environments can teach assembly effectively, backed by its p<1% mark improvement over six cohorts. The trade-off structure is instructively opposite to UNLV's: Reading used QEMU full-system emulation of a foreign ISA (ARM guest on x86 hosts), which changed the course's target architecture to whatever the emulator provided but preserved a fully native toolchain — GDB, breakpoints, and register inspection all worked inside the guest — whereas UNLV's amd64-only image preserves the course's real x86-64 ISA and Linux ABI at the cost of a documented gdb/ptrace limitation under QEMU user-mode emulation on Apple Silicon. In other words, Reading sacrificed ISA authenticity to keep the debugger; UNLV sacrifices the debugger on one host family to keep ISA authenticity, and the UNLV paper can frame this as full-system versus user-mode emulation rather than a defect unique to its design. The distribution comparison is also useful: Reading's 1 GB zip/USB image with a shared login, student-managed apt-get updates, and a decade-old pinned Ubuntu 9.04 contrasts with Docker's registry-based image distribution, reproducible builds, and UNLV's browser-based code-server front end, and Reading's own students' struggles with vim and console Linux (30% found Linux hard in 2010) motivate UNLV's choice of a familiar VS Code interface.

## Using Virtual Machines to Enhance the Educational Experience in an Introductory Computing Course

**Citation:** David P. Harvie, Jason R. Cody, Christopher Morrell, and Tanya T. Estes (2019). Using Virtual Machines to Enhance the Educational Experience in an Introductory Computing Course. In The 20th Annual Conference on Information Technology Education (SIGITE '19), October 3–5, 2019, Tacoma, WA, USA. ACM, pages 28–32. DOI: https://doi.org/10.1145/3349266.3351401.
**Filename:** `VMs in intro computing.pdf`

**What it is:** This paper describes and evaluates giving every student in a sophomore-level survey course a personal Linux virtual machine, hosted on the department's own virtualization infrastructure, to simplify installation of required server software and to reinforce understanding of client-server networking. The impact was assessed by tracking the change in software installation and troubleshooting time and student performance across two academic years and ten classrooms. The authors report that VMs improved classroom efficiency, recovered instruction time previously lost to software installation, and sustained or improved student performance on graded events.

**Setting & method:** The setting is a sophomore-level survey course of Computer Science and Information Technology topics at the United States Military Academy at West Point, which introduces MySQL, MongoDB, HTML/CSS, JavaScript, and the Meteor web application framework, and previously required students to install all servers and tools on their personal Windows laptops. The study compares Academic Year 2018 (students installed all software on personal computers) against Academic Year 2019 (all students installed server software on individual Ubuntu VMs instead), across ten classrooms with N=89 students in AY2018 and N=92 in AY2019. Five dependent variables were measured: class installation time (time to install software on more than 90% of student systems), class software troubleshooting time (instructor-reported), scores on a 50-point networking quiz, performance on eight networking questions on the final exam, and scores on the culminating dynamic web application project built with Meteor; quiz and project distributions were compared with two-tailed t-tests. The motivating pain was concrete: installation troubleshooting "regularly consumed 15-20 minutes of a 55-minute class," and in October 2017 a mid-lesson Meteor update from version 1.5 to 1.6 left half the class on the previous version and half on the updated one.

**Key findings:**
- Class installation time dropped from 75–100 minutes of class time in AY2018 (five installation lessons at 15–20 minutes each) to 35–50 minutes total in AY2019 (7–10 minutes in each of the five installation lessons).
- Troubleshooting time dropped from approximately 65–90 minutes across the 13 programming lessons in AY2018 (instructors commonly reported spending 5–7 minutes per lesson troubleshooting a single student's software suite) to 26–65 minutes in AY2019 (3–5 minutes per lesson).
- Networking quiz scores rose from an average of 70.2% (median 72.9%, SD 16.9%, N=89) in AY2018 to 76.8% (median 80.0%, SD 14.3%, N=92) in AY2019; "Applying a 2-tailed T-Test to the data resulted in a T-Test score of 0.00160 (i.e. confidence of > 98%)."
- Web application project scores rose from an average of 79.3% (median 84.7%) in AY2018 to 90.8% (median 95.8%) in AY2019, with a two-tailed t-test score of 0.0000102 (confidence > 99.9%); the authors surmise students did better because they could get their applications working on their VMs instead of "trying unsuccessfully to deploy to a separate server," where most previous-year students had failed for administrative reasons beyond their control.
- Performance on networking questions on the final exam was practically unchanged: 89.7% correct in AY2019 (660 of 736 question instances) versus 90.2% in AY2018 (642 of 712), a 0.5% decrease, suggesting both cohorts converged by exam time.
- The department's EECSNet virtual environment (VMware ESXi/vCenter on seven physical hosts plus a storage area network, totaling 273.24 GHz of compute, 2.19 TB of memory, and 100 TB of shared network storage) has run as many as 700 machines concurrently; each student VM had three accounts (student with sudo, instructor, and root restricted to the administrator).
- Instructors could log into student VMs to grade the web project against both source code and the running application, and could revert student VMs to stored snapshots to rescue botched installations; the course deliberately did not preinstall MySQL, MongoDB, and Meteor, instead having students install them with APT so they would "gain practical experience and knowledge of program and package management in a Linux environment."

**Technical approach:** The system is server-side, institution-hosted full virtualization rather than containers: one Ubuntu VM per student and one per instructor per section, provisioned on the department's EECSNet VMware ESXi/vCenter environment (seven physical hosts, Dell/EMC storage appliance, 273.24 GHz compute, 2.19 TB RAM, 100 TB networked storage). Students access their VMs over SSH and Bash from their personal Windows laptops, configure client tools such as MySQL Workbench on the host to talk to servers on the VM (practicing addresses, protocols, and ports for a real client-server architecture), and install all course software themselves via Ubuntu's APT. EECSNet deliberately segregates the educational network from the university's production network so that student mistakes (such as a rogue DHCP server) cannot damage production IT. Snapshots provide revert-to-baseline recovery, and the faculty rely heavily on scripted automation for VM creation, maintenance, and deletion because the university's IT support staff do not administer the environment.

**Limitations the authors acknowledge:** The authors state that the regained classroom time "may have resulted in better student comprehension but more data is needed to adequately assess" the effect, and the second hypothesis (that VM-based client-server practice improves networking comprehension) received only partial support, since final-exam networking performance was essentially identical across years and the course is introductory, so the hypothesis may need adjusting toward initial comprehension rather than lasting gains. They also identify day-to-day operation and maintenance as one of the biggest challenges, because IT support does not provide the environment and "the configuration, virtual machine build-out, and maintenance of the system falls of the faculty," worked around with heavy scripted automation. Finally, they discuss cloud hosting as an attractive alternative but caution that cloud providers charge for usage while on-premises costs (power, cooling, hardware replacement, administration) are simply less apparent, encouraging anyone considering a move to the cloud to weigh all current costs.

**Relevance to the UNLV Docker IDE paper:** This paper is the clearest quantitative demonstration in the set that standardizing the environment converts installation and troubleshooting time back into instruction time (75–100 minutes down to 35–50, with significant gains on the quiz and project), and those instructor-time metrics form a ready methodological template for evaluating the UNLV images. As a design point it is a contrast case: West Point centralizes VMs on department-owned VMware infrastructure that faculty must build and maintain themselves, while the UNLV approach pushes a prebuilt Docker image to each student's own machine, eliminating both the server fleet and the faculty sysadmin burden the authors complain about. Their pedagogical choice to leave server software uninstalled so students practice APT package management is the opposite of the UNLV images' fully preinstalled toolchains, which is a useful axis (environment-as-content versus environment-as-invisible-substrate) for the UNLV paper to position itself on. Their snapshot-based revert-to-baseline recovery is also the VM-era analogue of container disposability, which the UNLV IDEs get for free from `docker run`.

## Using DevContainers to Standardize Student Development Environments: An Experience Report

**Citation:** Sander Valstar, William G. Griswold, and Leo Porter (2020). Using DevContainers to Standardize Student Development Environments: An Experience Report. Proceedings of the 2020 ACM Conference on Innovation and Technology in Computer Science Education (ITiCSE '20), Trondheim, Norway. DOI: https://doi.org/10.1145/3341525.3387424.
**Filename:** `DevContainers.pdf`

**What it is:** This is an experience report on replacing pre-configured campus Linux servers with DevContainers — Docker images configured via VS Code's `.devcontainer` mechanism — so that students in a large C++ course can run a standardized development environment on their own machines. The authors give students a choice between the traditional ssh-accessible Linux servers and the DevContainer, then measure which option students chose, why, what problems arose, and what the setup cost the instructional team. The stated aim is "to evaluate how well students value this development environment while providing sufficient details for faculty to adopt our approach in their courses."

**Setting & method:** The study took place at the University of California, San Diego (described as a large public research-focused institution in North America with IRB approval), in an upper-division Advanced Data Structures course taught in C++ with four programming assignments; the course had a total enrollment of 449 students across 3 sections and 2 instructors, with 2 graduate TAs, 11 undergraduate head tutors, and 26 undergraduate tutors, and the authors studied 416 students. Students could freely choose between the DevContainer and the campus Linux servers; data came from a demographic survey in week one (N=202 with both demographics and preference data), an end-of-term survey attached to the last assignment, analysis of Piazza posts and the instructional team's Slack channel, and a voluntary anonymous staff survey (11 of 41 members responded). Open-ended survey responses were processed with NLTK using word collocation (trigram) analysis. Five research questions covered student preference and reasons, effects on underrepresented groups, perceived advantages and disadvantages, cost to the instructional team, and staff opinions.

**Key findings:**
- 71% of students developed in the DevContainer versus 29% on the Linux server; 70% recommended or strongly recommended the DevContainer (only 8% against), while the Linux server was recommended by 28% and 34% would not recommend it.
- The top student reasons for preferring the DevContainer were liking the VS Code editor (7 mentions in the trigram analysis), the convenience of working locally versus over ssh (5), wanting to try something new (2), not requiring an internet connection, and freedom to work from anywhere; the top reasons for preferring the Linux server were familiarity with it and Vim from prior courses (4), the DevContainer taking too much time to get working (3), a recurring "reconnecting"/VS Code freeze issue (2), and underpowered laptops.
- On setup difficulty, 18% found the DevContainer difficult or very difficult to set up while 35% found it easy or very easy; 35% said they needed help setting it up versus 39% who did not. For the Linux server account, 52% needed no help and only 17% needed help — which the authors attribute to prior familiarity from earlier courses.
- Support-traffic counts favored the DevContainer despite its larger user base: 98 Piazza posts (of over 3,000 total) mentioned the DevContainer/Docker versus 108 for the Linux server, and the staff Slack channel (over 12,000 messages) had 120 DevContainer-related messages versus 147 for the Linux server.
- On the staff survey, 64% agreed or strongly agreed with "I had to help many students with setting up their DevContainer" (18% disagreed), versus 9% agree and 64% disagree for the Linux server; nonetheless the instructional team "overwhelmingly recommended instructors in future terms to use a DevContainer with no one recommending against using it."
- For the demographic subsample (N=202: 68% men, 29% women, 3% non-binary; 64% Asian, 19% Caucasian, 9% Hispanic/Latinx, 0% Black, 7% other), almost all groups showed more than 60% preference for the DevContainer (75% among Asian-identifying students; students identifying as other races/ethnicities slightly preferred the Linux server at 53%), and chi-squared tests at the 0.05 significance level "found no significant correlation between gender or race/ethnicity and a stronger preference for the DevContainer or the Linux server."
- Reported DevContainer disadvantages were poor handling of large data files and datasets, heavy disk and memory consumption, running "significantly slower" on some laptops, and initial setup time; Linux server disadvantages were having to use Vim instead of VS Code (6), logging in over ssh every time (4), needing a stable internet connection (3), and being less user friendly (3).
- Motivating context: 44% of students owned Windows machines and 46% owned Macs, while the autograder ran Linux tools (GCC, GDB, Valgrind); the campus lab machines' software "were roughly five years out of date" because reconfiguration through a third party took two weeks.
- The authors argue the setup burden is front-loaded: "After a student has a working Docker installation, running the DevContainer is as simple as the click of a single button."

**Technical approach:** The system is Microsoft VS Code's DevContainer integration on top of Docker: a hidden `.devcontainer` directory in the project root holds `devcontainer.json` (naming the container, listing VS Code extensions to install, and mapping directories into the container), a Dockerfile (typically `FROM ubuntu:18.04` with `RUN apt-get`/`yum` commands to install course tools such as GCC, GDB, and Valgrind), and optionally a `docker-compose.yml`; because the configuration lives in the repo, it is version-controlled and any student who checks out the code gets the environment, and VS Code prompts "Reopen in Container" with a single click. The instructional team published their setup at https://github.com/sandervalstar/iticse_devcontainer_demo, and the same Docker configuration can be reused unchanged by autograders such as Gradescope. Students only needed to install Docker and VS Code; the paper notes one caveat that Docker on Windows requires Hyper-V, which Windows Home edition lacks (students can upgrade free to Windows Education edition), and Section 3.1.1 discusses containers versus VMs, including that Docker on Windows runs a small Linux VM shared by all Linux containers (with LCOW/Hyper-V isolation as an experimental alternative at the time). GitHub Codespaces is not mentioned, and neither Apple Silicon nor CPU-architecture (amd64/arm64) issues appear — the paper predates Apple Silicon.

**Limitations the authors acknowledge:** In the Threats to Validity section, the authors acknowledge that a major driver of the DevContainer preference was really a preference for VS Code, which students could also have obtained by connecting to the Linux server via VS Code's ssh function, though many students may not have known about that option. They also acknowledge that the first author was a teaching assistant for the course and "may have imparted his enthusiasm for DevContainers to the students or course staff." Additionally, they note that some underrepresented demographic groups in the sample were quite small, making it hard to attach statistical significance to the subgroup preference findings, and they hypothesize (without direct evidence) that the observed setup difficulties would occur mainly in the first course in a curriculum that introduces DevContainers.

**Relevance to the UNLV Docker IDE paper:** This is arguably the closest prior work and a natural anchor citation: it is the canonical ITiCSE experience report on giving students a Docker-standardized, instructor-controlled course environment for C++ with GCC/GDB/Valgrind — the same toolchain and the same "it works on my machine" and autograder-parity motivations as the UNLV C++ image. It also serves as a methodological template for an experience report: research questions on preference, equity, advantages and disadvantages, and staff cost; end-of-term surveys with concrete percentages; and forum/Slack traffic counts as a support-load proxy are all directly reusable measures for evaluating the UNLV IDEs. The key contrasts are architectural: Valstar et al. rely on locally installed VS Code plus the Remote-Containers extension and never confront CPU architecture at all, whereas the UNLV work uses code-server in the browser (removing even the VS Code install step), builds multi-arch amd64+arm64 images, and makes a deliberate pedagogical choice to keep the assembly image amd64-only with a documented gdb/ptrace-under-QEMU limitation on Apple Silicon — a design tension that simply did not exist in 2020. Finally, the paper's finding that Docker installation was the single hardest setup step, and its "reconnecting" and laptop-resource complaints, give the UNLV paper concrete prior pain points to compare against its own localhost-only, AI-disabled code-server deployment.

## Lightweight Symphony: Towards Reducing Computer Science Student Anxiety with Standardized Docker Environments

**Citation:** Kourtnee Fernalld, TJ OConnor, Sneha Sudhakaran, and Nasheen Nur (2023). Lightweight Symphony: Towards Reducing Computer Science Student Anxiety with Standardized Docker Environments. In The 24th Annual Conference on Information Technology Education (SIGITE '23), October 11–14, 2023, Marietta, GA, USA. ACM. DOI: https://doi.org/10.1145/3585059.3611432 (ISBN 979-8-4007-0130-6/23/10, CC BY 4.0).
**Filename:** `Lightweight Symphony.pdf`

**What it is:** This is an experience report on deploying standardized, instructor-built Docker container environments in three undergraduate computer science courses to counter the heterogeneous, decentralized student hardware landscape that emerged after pandemic remote learning. The authors hypothesize that a stable, standard environment reduces student anxiety, and they test this with pre-, mid-, and post-semester surveys. They also publish their build scripts, images, and tutorials at https://github.com/FITSEC/docker-images.

**Setting & method:** The study took place at the Florida Institute of Technology (L3 Harris Institute for Assured Information / ECE-CS department) during the Fall 2022 16-week semester, across three courses with a combined enrollment of N=188: Fundamentals of Software Development 1 (first-year Java), Operating Systems Concepts (third-year, OS161), and Introduction to Cybersecurity (an elective with eight hands-on labs and a semester-long CTF). Students received training in deploying Docker, mapping the local filesystem, connecting to network resources, and basic troubleshooting, then completed three optional anonymous Google Forms surveys (six multiple-choice, nine yes/no, two 5-point Likert, two 10-point Likert, and twelve open-response questions) measuring Docker adoption, setup difficulty, and self-reported anxiety on a 1–10 scale calibrated against the GAD-7 instrument (score 7 chosen as the "high anxiety" threshold). Over 22% of enrolled students responded: 59 initial, 45 mid-course, and 42 end-of-course responses.

**Key findings:**
- Adoption and perceived benefit: "84% of students adopted our standardized environments, with 75% indicating it contributed to their success." By semester's end, 69.2% reported the standardized environment specifically helped reduce their anxiety, and 86.8% reported the environment worked well for their course.
- Overall self-reported anxiety fell from 4.8 ± 2.4738 (pre) to 4.1 ± 2.4292 (midterm) on the 1–10 scale; setup difficulty averaged 2.4 ± 1.1998 on a 1–5 scale.
- Per-course anxiety: Software Development 4.2222 ± 2.8191 initial versus 4.3333 ± 2.958 midpoint; Operating Systems 5.8333 ± 2.4070 versus 4.6428 ± 2.2397; Cybersecurity 5.1724 ± 2.3914 versus 3.75 ± 2.4251. High-anxiety (>=7) rates went 0% to 33.4% in the intro course (an increase), 24.1% to 19.1% in OS, and 41.2% to 14.2% in Cybersecurity.
- Adoption split by level: 100% adoption in the Cybersecurity and Operating Systems courses versus 78% in the first-year Software Development course.
- Image details (provided to 188 students): Software Dev 2.29 GB on ubuntu:20.04 (noVNC, Java JDK/JRE, text editors; 105 Docker pulls); Operating Systems 3.48 GB on ubuntu:20.04 (OS161 and dependencies; 42 pulls); Cybersecurity 8.27 GB on kalilinux/kali-rolling (over 140 apt packages; 132 pulls). The initial Cybersecurity build required 20.5 GB and was reduced to 8.27 GB using Docker build-optimization documentation.
- Distribution logistics: student-side builds failed cross-platform (M1 MacBooks built ARM Linux images instead of the required AMD64), so the team built all images on an AMD64 Linux machine and pushed them to DockerHub, which for $60 annually supports 5,000 daily image pulls, five concurrent builds, and 300 vulnerability scans; students then ran a single one-liner to pull, map a folder, start, and attach.
- Hardware baseline (pre-survey, N=59): 28 personal Windows machines, 11 older Macs, 9 M1/M2 Macs, 9 Linux, 2 school Windows machines, 0 Chromebooks; only 6 of 59 had ever used Docker.
- Apple Silicon payoff: "Using the Docker environment was particularly helpful to students with the M1 and M2 MacBooks to avoid configuring a VM on an ARM architecture."
- Institutional friction: deploying Docker plus WSL to the university's restricted Windows 11 lab workstations took four weeks of IT effort; the team also spent four weeks before the semester testing images on different workstations, operating systems, and architectures.
- On cloud-hosted alternatives (GitHub Codespaces), quotable verbatim: "While this approach may satisfy introductory programming courses, it does not scale to meet the needs of more complex coursework like operating systems, databases, networking, cybersecurity, or machine learning." This is their stated justification for student-local containers over cloud hosting.

**Technical approach:** The system is pure Docker container-based virtualization (explicitly contrasted with Type-2 hypervisors like VMware and VirtualBox, which cannot run AMD64 guests on ARM hosts and demand heavy RAM and disk reservations, e.g., Ubuntu's recommended 8 GB memory and 25 GB storage). Each course got a custom image built from a Dockerfile: the first-year image extended a community docker-ubuntu-novnc base so novice students could reach a graphical desktop through a web-browser VNC (noVNC) session, the OS course image (no browser VNC, assuming higher literacy) bundled OS161 and dependencies from a prior student's container, and the cybersecurity image was a Kali-rolling build with 140+ apt packages replacing the instructor's former 40+ GB quarterly VMware images. Images were compiled centrally on AMD64/Linux, hosted on DockerHub, and consumed via a single pull/run one-liner with a mapped local folder for file transfer; Docker's multi-platform support (x86-64, ARM, MIPS, PPC64LE, S390X) is cited as the enabler for hybrid classrooms mixing M1/M2 MacBooks, Intel Macs, and Windows desktops.

**Limitations the authors acknowledge:** The survey response rate was modest (just over 22% of the 188 enrolled students, and only 42 completed the final survey), and results rest on optional, anonymous self-report. First-year students struggled with adoption: they had difficulty following the installation instructions even after the team rewrote and redistributed them, high-anxiety rates in the introductory course actually rose from 0% to 33.4% (attributed possibly to the newness of the environment or of university coursework generally), and adoption there was only 78% versus 100% in upper-level courses. The authors note that instructor buy-in strongly shaped adoption (a GSA-led, lightly emphasized introduction produced mixed uptake, while the OS instructor's strong push produced 100%), that their managed Windows Domain lab environment required ticket-based IT intervention and four weeks to get Docker and WSL installed, and that "further research is necessary to understand the benefits of integrating lightweight virtualization in the classroom."

**Relevance to the UNLV Docker IDE paper:** This is arguably the closest prior work for the UNLV paper: instructor-built, course-specific Docker images distributed to students on heterogeneous personal hardware, with the amd64-versus-arm64 architecture problem confronted head-on — their observation that M1 MacBooks silently built ARM images instead of the required AMD64, and their fix of centrally prebuilding and registry-hosting images, directly parallels UNLV's decision to publish a multi-arch (amd64+arm64) C++ image while keeping the assembly image deliberately amd64-only. It also supplies a useful contrast case on ISA fidelity: Fernalld et al. treat cross-architecture usability as a pure win for M1/M2 users, whereas the UNLV assembly course pins the real x86-64 ISA and Linux ABI and documents the gdb/ptrace breakage under QEMU emulation that Lightweight Symphony never probes. Their browser-delivered environment is noVNC (a remote desktop) rather than code-server, so UNLV can position browser VS Code as a refinement of the same accessibility goal, and their survey design (pre/mid/post anxiety instruments referenced to GAD-7, adoption rates, setup-difficulty Likert items) offers a ready methodological template for evaluating the UNLV IDEs. Finally, their related-work argument that cloud-based Codespaces "may satisfy introductory programming courses, [but] does not scale to meet the needs of more complex coursework like operating systems, databases, networking, cybersecurity, or machine learning" (full quote in Key findings above) supports UNLV's local-first, localhost-only design framing — and pairs directly with Malan's Containerizing CS50, where the cloud approach works precisely because CS50 *is* an introductory course. (Caution when citing: this is a related-work claim, not something they empirically demonstrated — Malan shows Codespaces running heavy containers at MOOC scale — so the defensible version of the argument is about cost, resource limits, and control, not literal impossibility.)

**Note — supports the philosophy, exposes its principal limitation (discussion 2026-08-16):** Lightweight Symphony validates the pre-built, registry-hosted, student-local container model — the same model as UNLV's — but its data shows the model worked far better for upper-level students than for novices. In the two upper-level courses adoption was 100% and anxiety dropped; in the first-year course adoption was only 78%, students struggled with installation instructions even after they were rewritten, and the high-anxiety share *rose* from 0% to 33.4%. Deferring compute to the student's machine means deferring some sysadmin work to the student too, and first-years are the least equipped to absorb it; Valstar et al. (DevContainers) independently found the same choke point, with Docker installation itself as the single hardest setup step. Two angles for the UNLV paper follow. First, a scoping argument: UNLV's CS 202/CS 218 students are not first-semester novices, and Lightweight Symphony's adoption split says that is exactly the population where local Docker works — the courses sit on the favorable side of the divide by design, not coincidence. Second, an honest limitations statement: the UNLV design reduces post-install friction relative to their noVNC setup (a single pull-and-run command, then VS Code in a browser at localhost), but the hard step both papers identify — installing Docker Desktop itself — is inherited in full and should be stated plainly rather than left for a reviewer to raise. One-sentence framing for the paper: Lightweight Symphony validates the student-local container model while demonstrating that its principal cost is front-loaded setup friction that falls hardest on novices — a cost the UNLV deployment reduces but cannot remove, since Docker installation remains the student's responsibility.

## Teaching CS50 with AI: Leveraging Generative Artificial Intelligence in Computer Science Education

**Citation:** Rongxin Liu, Carter Zenke, Charlie Liu, Andrew Holmes, Patrick Thornton, and David J. Malan (2024). Teaching CS50 with AI: Leveraging Generative Artificial Intelligence in Computer Science Education. In Proceedings of the 55th ACM Technical Symposium on Computer Science Education V. 1 (SIGCSE 2024), March 20–23, 2024, Portland, OR, USA. DOI: https://doi.org/10.1145/3626252.3630938.
**Filename:** `cs50 with ai.pdf`

**What it is:** This paper chronicles how Harvard's CS50 team developed and integrated a suite of AI-based teaching tools, collectively powered by a web application called CS50.ai, into their introductory computer science course starting in Summer 2023. The centerpiece is the "CS50 Duck" (ddb), a GPT-4-powered chatbot with pedagogical guardrails that guides students toward solutions rather than giving answers outright, alongside VS Code extensions for explaining highlighted code and improving code style. The stated goal was to approximate a 1:1 teacher-to-student ratio through software, while banning commercial AI tools such as ChatGPT, GitHub Copilot, and the new Bing per course policy.

**Setting & method:** The work took place at Harvard University in CS50, the university's introductory computer science course for majors and non-majors, which also has a global online presence via OpenCourseWare and a MOOC with more than 5 million registrants. Tools were deployed first to approximately 70 summer students in Summer 2023, then to thousands of students online, and finally to approximately 500 on-campus students in Fall 2023. Evaluation combined a non-anonymous end-of-course survey of the roughly 70 summer students, two non-anonymous surveys of the approximately 500 Fall 2023 on-campus students (mid-semester and end of semester, with 73% responding to the latter), a manual accuracy review of all 64 CS50 Duck answers posted on the Ed discussion forum during summer (reviewed by a senior course staff member separate from the development team), a preliminary review of 180 Fall 2023 Ed answers, and platform usage telemetry through December 2023.

**Key findings:**
- Summer 2023 accuracy review of 64 Ed answers: 22 of 25 (88%) curricular answers were correct and 30 of 39 (77%) administrative answers were correct; the authors note this compares favorably with recent work indicating "ChatGPT is correct only 48% of the time when addressing software engineering topics."
- Preliminary Fall 2023 Ed data: only 70 of 180 CS50 Duck answers were "endorsed" by human staff, suggesting an accuracy of only 39%, but the authors suspect this understates true accuracy because Ed usage dropped (average questions per student via Ed: 0.89 in Fall 2022, 1.1 in Summer 2023, 0.28 in Fall 2023) as students shifted to the Duck in VS Code and the CS50.ai website.
- Fall 2023 mid-semester survey (~500 students): 17% used the tools more than ten times a week, 32% used them 5–10 times a week, 26% used them 2–5 times weekly, 25% less than twice per week; 47% found them "very helpful," 26% "helpful," 21% "somewhat helpful," 6% "not helpful"; on effectiveness, 35% "very effective," 35% "effective," 25% "somewhat effective," 5% "not effective"; on confidence in response accuracy, 23% "very confident," 46% "generally confident," 27% "somewhat confident," 4% "not confident."
- Fall 2023 end-of-semester survey (73% response rate): 50% used the tools "frequently" and 28% "constantly," 19% "infrequently," 3% never; 33% found them "always helpful," 55% "frequently helpful," 11% "infrequently helpful," 1% "never helpful"; 53% of students "loved" them, 33% "liked" them, 13% were neutral, 1% "disliked" them.
- Usage scale: more than 50,000 unique users of CS50.ai as of December 2023 and more than 1.8 million queries processed; daily unique active users grew from approximately 200 in June 2023 to 1,000 in September 2023 and 1,500 by November 2023; daily prompt creations peaked at 25,000 per day, with 15–20K prompts typically created per day; average prompts per user per day rose from 5 to 15.
- Cost: approximately $1.90 per student per month and $0.05 per prompt, which the authors call "a worthwhile investment given the positive student feedback and enhanced learning experience."
- Usage throttling: each student starts with 10 "hearts," each Duck interaction consumes one, and one heart regenerates every three minutes, both to control GPT-4 costs and to promote thoughtful questioning.
- Student reception was strongly positive; one student wrote it was "absolutely unreal. felt like having a personal tutor... i love how AI bots will answer questions without ego and without judgment," and the abstract notes students "felt like they had 'a personal tutor.'"
- CS50.ai has since been extended to 10 other CS50-related MOOCs (game design, SQL, cybersecurity, and more) via a modular configuration system.

**Technical approach:** CS50.ai is a unified web application backend that mediates all communication between users and GPT-4 hosted on Microsoft Azure OpenAI; student queries have personally identifiable information removed, are converted into structured prompts with course-specific rules and guidelines (multiple YAML configuration files with distinct system prompts and user prompt templates per use case), and are answered via OpenAI's Chat Completion API. Retrieval-augmented generation grounds lecture-related answers: English lecture captions are segmented into short self-contained 30-second segments, embedded with OpenAI's text-embedding-ada-002 model, stored in a ChromaDB vector database, and the top-N most relevant segments are supplied to GPT-4 alongside each query. Front ends include a standalone CS50.ai website, a CS50 Duck VS Code extension, an "Explain Highlighted Code" VS Code extension, a reimplemented style50 as a VS Code extension with an "Explain Changes" button, and an Ed discussion-forum bot integrated via HTTP requests whose answers are subject to endorsement, amendment, or deletion by human staff. A prompt-injection "guard" checks every request for atypical non-alphanumeric patterns, consults GPT-4 through an independent API call to classify suspected attacks, and aborts the user session if an attack is confirmed; heart-based usage throttling limits interaction rate. Notably for infrastructure comparisons, the AI tools live inside CS50's VS Code environment, and the paper describes no containerization or ISA-level concerns — the system is a cloud-hosted LLM service layered onto the course's tooling.

**Limitations the authors acknowledge:**
- CS50.ai occasionally "hallucinates" incorrect information and, like other AI chatbots, "tends to exhibit a tone of complete and authoritative confidence even when wrong, while humans might qualify the certainty of their answers."
- Administrative-question accuracy (77%) lagged curricular accuracy because GPT-4's training data has a time cutoff and the evolving CS50 syllabus caused it to be out of sync with the course's latest changes.
- The apparent Fall 2023 accuracy drop to 39% on Ed is based on data they had only just begun reviewing, and their explanations for it (shifting usage patterns, students escalating harder questions to Ed) "are only conjectures at this point in time."
- Surveys were non-anonymous, which the authors note without elaborating on response bias, and some students wanted the usage throttling removed, which the team retains for cost and pedagogical reasons.

**Relevance to the UNLV Docker IDE paper:** This is the natural contrast and policy-framing citation for the UNLV paper's deliberate decision to ship code-server-based course IDEs with AI features disabled: CS50 argues that a guardrailed institutional AI beats forbidding AI outright, whereas the UNLV images take the opposite default, and citing this paper lets the UNLV work frame that choice as a considered position within an active pedagogical debate rather than an omission. The CS50 evidence also supplies the strongest argument for why disabling AI is defensible in specific courses — even Harvard's guardrailed GPT-4 hallucinated with authoritative confidence and hit only 88%/77% accuracy — which matters more in an x86-64 assembly course where an LLM confidently misexplaining ISA/ABI details or gdb behavior would undercut the exact low-level fidelity the amd64-only image exists to preserve. There is a useful architectural contrast as well: both projects meet students inside VS Code-family tooling, but CS50.ai is a centralized, cost-bearing cloud service ($1.90/student/month, Azure-hosted GPT-4, PII scrubbing, prompt-injection guards), while the UNLV IDEs are localhost-only Docker containers with no external service dependency, no per-student cost, and no data leaving the machine — consistent with the project's documented local single-user threat model. Finally, CS50's banning of commercial tools (ChatGPT, Copilot, Bing) while providing a sanctioned alternative shows that course-level AI policy is enforced through the provided environment itself, which is precisely the lever the UNLV images exercise by disabling AI features in the shipped code-server configuration.

## Containerizing CS50: Standardizing Students' Programming Environments

**Citation:** David J. Malan (2024). Containerizing CS50: Standardizing Students' Programming Environments. In Proceedings of the 2024 Innovation and Technology in Computer Science Education V. 1 (ITiCSE 2024), July 8–10, 2024, Milan, Italy. ACM. DOI: https://doi.org/10.1145/3649217.3653567.
**Filename:** `Containerizing CS50.pdf`

**What it is:** This is an experience report arguing for Docker containers as an alternative to clusters of servers or virtual machines for standardizing students' programming environments in introductory courses. It traces the evolution of CS50's environments at Harvard from an on-campus Linux cluster, to an off-campus AWS cloud, to a client-side "CS50 Appliance" VM, to Docker-backed web IDEs (the Cloud9-based CS50 IDE, then VS Code atop GitHub Codespaces), discussing the pedagogical and operational trade-offs of each. The author concludes that the current SaaS-style adaptation of VS Code atop Codespaces is the most successful implementation to date.

**Setting & method:** The setting is CS50 at Harvard University, the institution's introductory programming course taught primarily in C and Python, with approximately 500 students each fall, 100 each spring, and a smaller summer cohort, plus a large OpenCourseWare/edX MOOC audience. This is not a controlled study but a longitudinal experience report spanning roughly 2007–2024 (containers in use since 2015), describing each successive environment, its motivations, and its failure modes. Outcomes are reported as cumulative usage counts, deployment and startup timings, and anecdotal student quotations rather than formal measurements; no experimental design, control groups, or statistical tests are used.

**Key findings:**
- More than half of CS50's students have never taken a computer science course before, and more than half describe themselves as "those less comfortable" with computing, motivating a standardized environment so term-start focuses on concepts rather than installing clang, gdb, valgrind, and python3.
- The client-side CS50 Appliance VM (introduced 2011) had a disk image of nearly 2 GB even with unneeded packages pruned, took hours to export and test after any package update, was slow to download and boot, struggled on lower-end netbooks, and suffered VirtualBox bugs — at one point "closing the lid of one's laptop with the VM still running could 'brick' it entirely."
- Containers start dramatically faster than VMs: "Thanks to containerization, students' programming environments now start within seconds rather than minutes." The paper also notes a VM might take minutes to boot while a container takes seconds, and that a server with resources for, e.g., 3 VMs might run, e.g., 14 containers.
- Prior to its deprecation, the Cloud9-based CS50 IDE was used by more than 500,000 students and teachers; since its debut in late 2021, CS50's adaptation of VS Code atop Codespaces has been used by more than 700,000 students and teachers, most recently averaging more than 1,000 active users per day and more than 10,000 per week.
- AWS Cloud9 initially assumed a VM-per-user model, which CS50 reconstructed as a container-per-student model orchestrated with Kubernetes "to reduce computational costs by an order of magnitude"; educational grants from AWS covered the cloud costs, and Docker, VS Code, and Codespaces are usable at no cost by teachers and students.
- Students described the environment as "accessible," "easy to use," and "helpful"; per one student, "I love how it allowed us to just focus on coding rather than setting up," and per another, "everything just worked."
- The web-based route was chosen deliberately over browser-only "toy" environments: the authors "were reluctant to provide students with a 'toy' environment, lest they not know how or where to write code after term's end," and browser security models prevent in-browser code from binding to TCP/IP sockets, which would block CS50's Flask web-app development.

**Technical approach:** The current system is a web-based adaptation of VS Code atop GitHub Codespaces: a web application at https://cs50.dev/ uses GitHub's Codespaces and Repos APIs to automatically create, within the course's GitHub organization, one repository per student with its own codespace (container) based on the course's Docker image `cs50/codespace`, then redirects students to GitHub-hosted containers; an application load balancer routes users to front-end web servers, with a database storing codespace metadata and a GitHub repository backing up each home directory. A committed `.devcontainer.json` preinstalls the course's VS Code extensions (e.g., ms-vscode.cpptools, ms-python.python) and settings (Bash as default terminal), and mid-semester image updates are deployed via a VS Code extension that prompts students to rebuild their container while preserving their files. The predecessor, CS50 IDE, was built atop AWS Cloud9 backed by a Kubernetes-orchestrated cluster of per-student Docker containers with persistent home directories, customized via Cloud9's SDK with a presentation mode, a GDB/MI-based graphical debugger, and a virtual rubber duck. The course image supports C, Python, C++, Java, JavaScript (Node.js), R, Ruby, and SQL (SQLite), with a preinstalled X server and VNC client for graphics; offline options include VS Code's Remote Development extension pack, running the container locally with Docker, and a headless `cs50/cli` image driven by the Python-based CS50 CLI (`cli50`); Dockerfiles are public at https://github.com/cs50/codespace and https://github.com/cs50/cli.

**Limitations the authors acknowledge:** VS Code's API is less featureful for extensions than Cloud9's in some ways, so the team has not been able to simplify VS Code's interface (hiding unneeded icons and buttons) to the extent they would like. Despite the goal of offboarding students from the cloud to their own PCs and Macs toward term's end, the authors "realized that we ourselves might not have facilitated such sufficiently" — one student reported "Not really sure how to set up an IDE on my computer directly." Results rest on usage counts and student quotations rather than controlled evaluation, and the approach depends on external providers (AWS grants, GitHub Codespaces) for cost coverage; the author also discloses having consulted part-time for GitHub as a Professor in Residence.

**Relevance to the UNLV Docker IDE paper:** This is the closest and most-cited prior work for the UNLV paper: it is the canonical argument that Docker-containerized, browser-based VS Code environments (Codespaces is essentially cloud-hosted code-server's commercial sibling) standardize introductory-course environments and let staff focus on teaching rather than technical support, which is exactly the motivation the UNLV C++ and assembly images inherit. It also serves as the sharpest contrast case: CS50 is cloud-hosted at MOOC scale with GitHub/AWS dependencies and now experiments with an AI chatbot, whereas the UNLV IDEs are deliberately local-only, localhost-bound, and AI-disabled — CS50's own acknowledged failure to offboard students to local machines ("Not really sure how to set up an IDE on my computer directly") directly supports UNLV's local-first design choice. Finally, CS50's single multi-language amd64 image contrasts with UNLV's per-course architecture decisions, especially the deliberately amd64-only assembly image preserving the real x86-64 ISA/Linux ABI; CS50 never confronts the Apple Silicon/QEMU gdb-ptrace issue the UNLV paper documents, which the UNLV paper can position as a gap in this prior work. Methodologically, Malan's experience-report structure (evolution of approaches, trade-offs, usage results, student quotes) is a workable template for the UNLV paper's own narrative.

**Note — container placement, not image distribution, is the real difference (discussion 2026-08-16):** Both CS50 and UNLV follow the same distribution pipeline: the maintainer runs the Dockerfile to build an **image** (the frozen, inert result of the build), pushes that image to a registry, and students (or GitHub) pull it. The Dockerfile only ever runs on the maintainer's machine; what students pull is the image, never a "container." The **container** — the live, running instance of the image — is created at `docker run` time and is the only part that executes. The entire architectural difference between the two projects is *where that container is instantiated*: for CS50/Codespaces it runs on GitHub's servers and the student's laptop just renders a browser tab, while for UNLV it runs on the student's own machine, which does all the compute. Two consequences follow, and both are paper-worthy. First, updates: image distribution is push-based for CS50 (rebuild the image and every new codespace silently converges on it) but pull-based for UNLV (publish a new tag to Docker Hub, then depend on students actually running `docker pull` — old versions linger and convergence cannot be forced). Second, hardware heterogeneity: Codespaces never confronts Apple Silicon because GitHub's servers are uniformly x86-64 and the student's chip is irrelevant; the moment compute is deferred to student machines, the project inherits whatever chips students bring, which is exactly where the amd64-only image's gdb/ptrace limitation comes from. In other words, the paper's two big threads — local-first vs. cloud-hosted, and the amd64-only ISA-fidelity decision — are the same decision (student-side container placement) viewed from two angles, a useful unifying observation for the discussion section. What UNLV buys with that decision: privacy (no telemetry, no account, nothing leaves the laptop), offline operation, zero hosting cost, no vendor dependency, and permanent student ownership of the environment (Malan's offboarding problem never arises). What it gives up: forced update convergence and immunity to student hardware diversity. UNLV's bind-mount workspace design is what keeps student containers disposable under this model — coursework lives outside the container, so a container can be destroyed and re-instantiated from the same pulled image without data loss or re-download.

## CodeDive: A Web-Based IDE with Real-Time Code Activity Monitoring for Programming Education

**Citation:** Park, H., Kim, Y., Lee, K., Jin, S., Kim, J., Heo, Y., Kim, G., & Kim, E. (2025). CodeDive: A Web-Based IDE with Real-Time Code Activity Monitoring for Programming Education. Applied Sciences, 15, 10403. DOI: https://doi.org/10.3390/app151910403.
**Filename:** `CodeDive.pdf`

**What it is:** This paper introduces CodeDive, a web-based programming environment built on a browser-accessible VS Code server that captures fine-grained, real-time behavioral data (code edits, compilations, executions, pauses) from students in university programming courses. Its stated purpose is twofold: to give instructors process-level visibility for timely support and learning analytics, and to uphold academic integrity in the era of LLMs by shifting assessment evidence from the final artifact to the developmental process. The system runs on a Kubernetes cluster with per-student containerized workspaces and an eBPF/inotify-based monitoring module called eWatcher.

**Setting & method:** The authors are affiliated with Jeonbuk National University, Incheon National University, and Kyungpook National University in South Korea, and the primary deployment took place in a Spring 2025 undergraduate Operating Systems course with approximately 100 enrolled students, of whom 95 produced at least one recorded snapshot, build, or execution during Assignment 1 (24 March to 4 April, roughly two weeks). The study is an observational systems-deployment evaluation rather than a controlled experiment: the authors measured captured event volumes (snapshots, builds, executions), build and execution success rates, adoption rate, system resource overhead, and stability, and they additionally ran CodeDive in parallel against another course of about 200 WebIDE containers as a load check. A separate semi-automated integrity-screening workflow was evaluated on Assignment 4 data, culminating in one confirmed academic-dishonesty case study.

**Key findings:**
- Adoption: 95 of ~100 enrolled students (95%) used the platform for Assignment 1, which the authors interpret as integration "without significant technical barriers."
- Captured volume over the two-week assignment: 24,845 snapshots (16,747,487 bytes total), 2,194 builds (1,618 successful, 576 failed), and 2,124 executions (2,011 successful, 113 failed); the average student produced about 261 snapshots, ~23 builds, and ~22 executions.
- Build success rate was approximately 74% (1618/2194) versus an execution success rate of approximately 95% (2011/2124), "underscoring that compiler errors were the primary hurdle for most students."
- Overhead: user-space collectors consumed on average 0.5% and 3% of a single CPU core and 100 MiB and 300 MiB of RAM, respectively; no detection delays or system overloads were observed from the kernel-resident eBPF tracer. The only incident was a briefly exceeded inotify watch limit early in the semester, which caused a small window of missed snapshot events and was fixed by raising the limit.
- Scalability: CodeDive simultaneously tracked about 200 WebIDE containers in another course with no degradation; the authors note this reflects deployed-course scale, not an architectural limit.
- Integrity screening: for Assignment 4, the average student recorded 37.96 successful builds, 10.87 failed builds, and 49.74 successful executions; flagging students in the bottom 25th percentile "enables TAs to focus their efforts on a high-priority group of 12 students instead of the entire class" (of 100). One flagged student's timeline showed step-function code growth (over 10,000 bytes added with only a single build failure) and the student later admitted to copying code from a peer.
- Quote likely to be cited: "By shifting evaluation from the final artifact to the developmental process, CodeDive offers a practical solution for comprehensively assessing student progress and verifying authentic learning in the LLM era."
- Quote on the snapshot mechanism: "the system will automatically generate a snapshot of the file's content if the user pauses typing for over one second after a file modification," a threshold chosen to match VS Code's default 1000 ms Auto Save afterDelay.

**Technical approach:** CodeDive comprises three layers: Common Services (an SPA Frontend, a Backend that validates JWTs issued by an external SSO such as Keycloak, and a primary/read-replica Main DB), the WebIDE (per-student, per-course VS Code server containers created on demand by an Instance Manager, fronted by a Router reverse proxy that hides container IP and port, with per-user Persistent Volumes in ReadWriteMany mode storing all code across a triple-replicated storage backend), and eWatcher, the monitoring module. eWatcher has two collection paths: eWatcher-proc uses a kernel-level eBPF program hooked on sched_process_exec (with a BPF hash map keyed by PID) to capture process start/stop events, command lines, working directories, and exit codes — chosen over ptrace for its lower context-switching overhead — while eWatcher-code uses inotify plus Python's watchdog and asyncio to detect file open/write/close events, with 8 KB fixed-size segment comparison and a one-second debounce to trigger full-file snapshots. Everything is deployed as pods on a Kubernetes cluster (eWatcher as a DaemonSet on every node) managed by YAML manifests or Helm charts, with seccomp-restricted non-root Security Contexts, namespace separation, NetworkPolicies, and per-student PVC plus RBAC enforcement so no container can mount another student's volume. Events land in dedicated Activity and Snapshots databases with three record types (Snapshot, Build, Execution), exposed through three REST analytics endpoints and visualized in an instructor dashboard featuring a cumulative code-change chart and an interactive per-student edit–build–run timeline.

**Limitations the authors acknowledge:**
- The deployment validates technical architecture only; a definitive assessment of educational impact "would require a comparative study with a control group," complemented by student surveys and interviews (including potential student anxiety) and longitudinal multi-semester analysis, none of which was performed.
- The fine-grained behavioral data collection necessitates a comprehensive ethical and data-protection framework (GDPR, FERPA); developing formal consent, access, deletion, and data-minimization policies and a compliance audit is stated as future work rather than something already in place.
- The one-container-per-student model is by design less memory-efficient than multi-tenant architectures and can create significant resource demands at peak; the paper offers only a qualitative cost discussion and defers a formal cost–benefit framework to future research.
- Kernel-resident eBPF tracer overhead "cannot be measured precisely from user space"; the 200-container scale reflects deployed courses, not a validated architectural limit, and formal stress tests and a sensitivity analysis of the snapshot threshold remain future work.
- The integrity-screening thresholds are decision-support heuristics, not an automated judge, and may vary by course and assignment; robust data-driven guidelines await data from more classes.

**Relevance to the UNLV Docker IDE paper:** CodeDive is directly citable prior work establishing that browser-delivered VS Code environments in per-student containers eliminate local-setup friction in systems programming courses — the same premise as UNLV's code-server-based C++ and x86-64 assembly images, and notably in a comparable course context (Operating Systems, C compilation with gcc in an integrated terminal). The sharpest contrast is architectural philosophy: CodeDive is a centrally hosted Kubernetes platform whose core value proposition is pervasive telemetry (eBPF process tracing, one-second-debounce file snapshots, instructor dashboards, plagiarism screening), whereas the UNLV design is localhost-only, single-user, and collects no telemetry at all — CodeDive's own admission that fine-grained behavioral capture triggers GDPR/FERPA obligations and consent frameworks is a strong argument the UNLV paper can cite for its no-monitoring, local-first stance. CodeDive also illustrates the cost side of centralization that UNLV avoids: SSO/JWT infrastructure, reverse proxies, replicated storage, and per-student cloud containers, versus a Docker image students run on their own machines. Finally, CodeDive's choice of eBPF specifically because ptrace-style tracing is too expensive provides a useful adjacent citation when the UNLV paper discusses its own gdb/ptrace limitation under QEMU emulation on Apple Silicon, and CodeDive's amd64-cluster homogeneity contrasts with UNLV's explicit multi-architecture (amd64+arm64) versus deliberately amd64-only ISA-fidelity decision, a dimension CodeDive never has to confront.

## Cross-Cutting Synthesis

**Recurring themes across the nine papers:**

1. **Standardization reclaims teaching time and reduces support load.** Every paper's core motivation is eliminating "works on my machine" variance: West Point measured installation time falling from 75–100 to 35–50 minutes of class time with significant grade gains on the project (p ≈ 0.00001); UCSD counted Piazza/Slack support traffic; CS50 repeatedly cites students who could "just focus on coding rather than setting up." The UNLV paper inherits this motivation directly and can cite the quantitative versions (Harvie et al., Cadenas et al.) alongside the experience reports.

2. **A clear infrastructure lineage: lab → cluster → cloud → VM appliance → container → browser IDE.** Laadan et al. (2010) and Malan (2013) document the VM-appliance generation and its failure modes (2 GB images, VirtualBox disk corruption, RAM pressure on weak laptops); Valstar et al. (2020), Fernalld et al. (2023), and Malan (2024) document the container generation; Malan (2024) and CodeDive (2025) converge on browser-delivered VS Code as the front end. The UNLV IDEs sit at the current end of this lineage: containerized, browser-delivered, but deliberately local rather than cloud-hosted.

3. **The local-versus-cloud tension is unresolved and cost-driven.** Cloud centralization gives staff visibility and uniform hardware (West Point's EECSNet, CS50's Codespaces, CodeDive's Kubernetes cluster) but costs money, sysadmin labor, or external-provider dependence (AWS grants, GitHub goodwill), and it fails offline. Local execution scales for free (Malan: 140,000 edX students were only feasible client-side) but forfeits staff access to student environments. Every centralized paper acknowledges its dependency; every local paper acknowledges the support-visibility loss.

4. **Hardware heterogeneity, and specifically Apple Silicon, arrived as a problem the literature has barely digested.** Papers before 2020 never mention CPU architecture except Malan's 32-bit-"for compatibility's sake" choice; only Lightweight Symphony (2023) confronts the amd64/arm64 split, and it treats emulated amd64 containers on M1/M2 Macs as an unqualified win without testing debugger behavior under emulation.

5. **The evaluation genre is the experience report.** Seven of nine papers are experience reports or systems papers evaluated with surveys, adoption counts, and support-traffic proxies; only Cadenas et al. and Harvie et al. present multi-year graded-outcome comparisons with statistical tests. This legitimizes an experience-report framing for the UNLV paper while suggesting that even modest concrete numbers (image sizes, startup times, per-platform test matrices) exceed the field's norm.

6. **AI is the newest fork in the road, and environments are the enforcement mechanism.** Teaching CS50 with AI shows a course banning commercial AI tools while shipping a guardrailed alternative inside its environment; CodeDive responds to LLMs by surveilling the coding process. Both demonstrate that the shipped environment is where AI policy becomes real, which is exactly the lever the UNLV images pull by disabling AI features in code-server.

**Gaps none of the nine papers cover, which the UNLV paper can claim:**

- **ISA fidelity as a deliberate design criterion.** No prior paper chooses a container architecture in order to preserve a course's real ISA and Linux ABI. Cadenas et al. made the opposite trade (adopting emulated ARM as the course ISA, keeping gdb fully functional inside a full-system guest), and Lightweight Symphony pushed amd64 images to ARM Macs without examining the semantic cost. The UNLV assembly image's deliberately amd64-only build is a design position with no direct precedent in this set.
- **Documenting debugger behavior under QEMU user-mode emulation.** None of the nine papers reports the gdb/ptrace limitation that arises when an amd64 container runs under user-mode emulation on Apple Silicon; the UNLV paper's documented characterization of this failure mode appears to be novel within this literature.
- **A per-course architecture decision framework.** Prior work ships one environment per course or institution; none contrasts two images from the same institution making opposite multi-arch decisions (multi-arch C++ versus single-arch assembly) for principled, course-specific reasons.
- **Localhost-only, zero-telemetry, AI-disabled as an articulated threat model.** The literature splits between cloud platforms that accept telemetry, accounts, and provider dependence, and local setups that simply do not discuss privacy. No paper frames local-only, single-user, no-data-collection, AI-off as a coherent design stance; CodeDive's GDPR/FERPA caveats and CS50's cloud costs supply the raw material for that argument, but the position itself is unclaimed.
